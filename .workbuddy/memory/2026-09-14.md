## 三轮：B8 时序实测 + 三处错误表述订正

用户问"为什么需要 commitEdit？不是本来就会先跑完 blur 再 layout 吗"。这个问题暴露了两个层次的事实，其中
**第二层把前一轮的推断也推翻了**（前一轮结论只记了"派发次数"，没记"时序"，于是把 Chromium 的派发时机
写反了，还写进了 `4ca027a` 的提交信息、CHANGELOG、代码注释和报告里）。

### 1. `blur` 根本不在通往 `layout()` 的路径上

`layout()` 唯一的上游是 `refresh()`（`interact.ts:520`）；`refresh()` 的入口是公开 API `refresh(data)`、
`initLeft/Right/Side/Down`（切方向）、`operationHistory.restore`（undo/redo）、compact/主题切换。
**这些路径都没有"用户离开编辑器"这个动作**——光标还在输入框里，`refresh()` 开头甚至是程序化的
`clearSelection()`。所以不存在"blur 先跑完、再 layout"的次序可依赖。用户付钱的那半句（"先点走再 layout"）
确实没问题，那本来就无 bug；出问题的是没人点走的那条路径。

### 2. 补测时序（Chromium）：blur 是**同步**派发的，且派发时元素**仍在文档中**

`b'(about:blank, host.innerHTML = '' 前/后各记一次)'`：

| 引擎 | 派发次数 | 时机 | 派发时 `isConnected` | `innerText` |
|---|---|---|---|---|
| Chromium | 1 | **同步**，在 `innerHTML=''` 赋值**过程中** | **true**（返回后才 false） | `"a\nb"` 完好 |
| Firefox | 0 | — | — | — |

→ 前一轮写的"Chromium 是在 detach 之后才派发、所以原路径在空树上 linkDiv"**是错的**。真实情况：blur
在元素仍连着时派发，所以 Chromium 上旧代码的提交其实**是对的**——这正是缺陷只在 Firefox 出现的机制解释。
（`commit()` 里那次 `linkDiv()` 在拆卸路径上确实多余，但那是因为 `refresh()` 之后还会再 linkDiv 一次，
不是"在空树上跑"；未修，见报告 B8。）

### 教训：测跨引擎行为时，"时序"必须和"次数"分开测

只记次数就会把 inline / async 搞混。探针要在赋值语句**前后各记一次**。已写进
`mind-elixir-bug-verify` skill 的第 5 节。

## 四轮：核验"正常操作能否触发 B8"（用户质疑 → 结论：用户对）

用户判断"正常操作不可能触发，开发者刻意这么做的话风险自担"。**核验后确认成立**，但过程值得记：

1. 先怀疑 `Ctrl+Z`：undo/redo 监听挂在 `mei.container`（`operationHistory.ts:207`，冒泡阶段），
   编辑框是它的后代 → 事件确实会冒泡上来。**但**两处内联编辑的 keydown 首行都是无条件
   `e.stopPropagation()`（`dom.ts:245` 主题编辑、`svg.ts:198` 摘要/箭头标签）→ 到不了 undo。
2. 写探针验证，**带阳性对照**：编辑中按 Ctrl+Z → `undo`/`refresh` 调用数 **0**，编辑框仍开、文本还在；
   关掉编辑器后在容器上按同一快捷键 → `undo` 被调 **1** 次。对照通过，证明探针不是"瞎通过"。
3. 枚举所有能在**编辑中**触达 `layout()` 的入口，全是程序化/宿主驱动：`refresh(data)`、
   `initLeft/Right/Side/Down`、`changeTheme`/`changeCompact`、`undo/redo`（键盘路径被
   stopPropagation 挡住）、`focusNode`/`cancelFocus`。→ 正常交互不可达。

**一个值得记的对照事实**：outliner 对"编辑中 Ctrl+Z"是**显式处理**的（`Outliner.ts:1279-1295`）——
先 `execCommand('undo')` 回退输入，若无效则 `active.blur()` **提交**、再 `stack.undo()`。
即"先提交再拆卸"这个约定在本仓确实存在，只是出现在它真正可达的地方（outliner 没用 stopPropagation，
改用 `document.activeElement` 判断）。

**关键机制区分**（别混）：`el.blur()` **显式调用**在所有引擎都会派发 blur；引擎分歧只出现在
"元素被移出文档导致的**隐式** blur"。所以 outliner 的 `active.blur()` 是可靠手段，而依赖移除动作则不可靠。

**待决策**：完全回退 B8 / 保留自动提交 / 只留 `commitPendingEdit()` 当宿主逃生口。
回退 B8 需同时删 `tests/edit-teardown.spec.ts` 与 CHANGELOG 条目，并与"修提交信息"合并成一次 amend。
