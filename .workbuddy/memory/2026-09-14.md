## 三轮：B8 时序实测 + 三处错误表述订正

用户问"为什么需要 commitEdit？不是本来就会先跑完 blur 再 layout 吗"。这个问题暴露了两个层次的事实，其中
**第二层把前一轮的推断也推翻了**（前一轮结论只记了"派发次数"，没记"时序"，于是把 Chromium 的派发时机
写反了，还写进了 `4ca027a` 的提交信息、CHANGELOG、代码注释和报告里）。

### 1. `blur` 根本不在通往 `layout()` 的路径上

`layout()` 唯一的上游是 `refresh()`（`interact.ts:520`）；`refresh()` 的入口是公开 API `refresh(data)`、
`initLeft/Right/Side/Down`（切方向）、`operationHistory.restore`（undo/redo）、compact/主题切换。
**这些路径都没有"用户离开编辑器"这个动作**——光标还在输入框里，`refresh()` 开头甚至是程序化的
`clearSelection()`。所以不存在"blur 先跑完、再 layout"的次序可依赖。用户付钱的那半句（"先点走再 layout"）
确实没问题，那本来就无 bug；出问题的是没人点走的那条路径。

### 2. 补测时序（Chromium）：blur 是**同步**派发的，且派发时元素**仍在文档中**

`b'(about:blank, host.innerHTML = '' 前/后各记一次)'`：

| 引擎 | 派发次数 | 时机 | 派发时 `isConnected` | `innerText` |
|---|---|---|---|---|
| Chromium | 1 | **同步**，在 `innerHTML=''` 赋值**过程中** | **true**（返回后才 false） | `"a\nb"` 完好 |
| Firefox | 0 | — | — | — |

→ 前一轮写的"Chromium 是在 detach 之后才派发、所以原路径在空树上 linkDiv"**是错的**。真实情况：blur
在元素仍连着时派发，所以 Chromium 上旧代码的提交其实**是对的**——这正是缺陷只在 Firefox 出现的机制解释。
（`commit()` 里那次 `linkDiv()` 在拆卸路径上确实多余，但那是因为 `refresh()` 之后还会再 linkDiv 一次，
不是"在空树上跑"；未修，见报告 B8。）

### 教训：测跨引擎行为时，"时序"必须和"次数"分开测

只记次数就会把 inline / async 搞混。探针要在赋值语句**前后各记一次**。已写进
`mind-elixir-bug-verify` skill 的第 5 节。

## undo/redo 避免全局渲染：方案讨论（用户拍板方向：**方案 B**）

问题：`restore()`（`operationHistory.ts:95`）走 `mei.refresh(snapshot)`，而 `refresh` =
`layout()`（`layout.ts:10` 一句 `nodes.innerHTML = ''`）+ `linkDiv()`（`linkDiv.ts:29` 清空 `lines`
+ 全量 `renderArrow`/`renderSummary`）。所以每次 Ctrl+Z 是 O(n) 建 DOM + O(n) 强制回流，
且选区/焦点全丢（要靠 `selectNodesByIds` 捞回来）。

**关键观察：正向操作已经是增量的**（`addChild`/`removeNodes`/`moveNode`/`expandNode` 都只
patch 局部再 `linkDiv`）。undo 贵不是架构限制，只是它走了"整树替换"这条最省事的路。

给过 5 个方案（A 定向回滚 inverse / B 快照 diff 增量 apply / C keyed reconciler /
D 局部 linkDiv / E rAF 合并 + 结构共享）。**用户选 B**，理由是它同时能加速 AI 渐进式输出。

### B 的设计要点（实现时按此）

- op 集合 5 种：`remove` / `insert(parentId,index,subtree)` / `move(id,parentId,index)` /
  `update(id,patch)` / `resync`（降级信号）。
- 三阶段不可换序：① 建 id→(parent,index) 索引 + 指纹剪枝（引用相等 / 子树指纹相等则整棵跳过）
  → ② 只读收集变更（先算 removed，再从 moved 候选里剔除）→ ③ 应用（写 DOM + 就地写数据，
  收尾只对脏主干 `linkDiv`）。
- 接口：`src/utils/treePatch.ts` 导出 `diffTree(current, target): TreeOp[]`（**纯函数、无 DOM、
  可 property test**）与 `applyTreeOps(mei, ops)`。
- **B 相对 A 的决定性优势**：A 必须逐步回放/前进，B 直接跳到任意目标态 → 流式输出天然"跳帧"，
  落后多少都不积压（每次只 diff「当前视图 vs 最新目标树」，中间态不参与）。
- **B 的收益上限被 D 卡住**：`linkDiv` 仍 `lines.innerHTML = ''`，所以 B 应与 D 一起做
  （main path 按 `(root→main)` 做 key 级 diff）。单节点 undo 的脏集 = 其所在主干。
- 安全网：应用后 dev 断言 `deepEqual(mei.getData(), target)`，不等或返回 `resync` 就回落 `refresh`。
- 从代码里读出的真实坑：
  1. **focus 模式**建议直接降级 refresh（focus 是 history 边界，本身会 clearHistory，命中率低）——
     否则要处理"全树快照 vs focus 子树"的 target 映射。
  2. **根节点不能 relocate**；跨 main container（lhs/rhs/down）的 move 与 direction 变更先降级 refresh。
  3. **`removeNodeDom(tpc, siblingLength)`** 靠 `siblingLength === 0` 决定是否收掉 expander +
     `.me-children`，批量删除必须按 parent 分组、用最终长度，不能逐条调。
  4. **折叠状态的隐藏子树**：current 里有数据但没 DOM，`findEle` 会 throw（它自己写了
     "maybe it's collapsed"）→ 不可见节点的变更只改数据、不产 op。
  5. **`tpc.nodeObj` 指针**指向 current 的节点对象 → 应用时必须 `Object.assign(currentNode, targetNode)`
     就地合并（`reshapeNode` 已是这个套路），不能替换对象，否则指针断裂。
  6. `update` 走 `shapeTpc`（它本身已是增量：`tpc.innerHTML=''` 后重建 tpc 内部），
     `expanded` 变化走 `expandNode(el, val, {silent:true})`。
  7. 增量路径下 DOM 复用 → `currentNodes` 引用仍有效，原有 selection restore 逻辑可保留。
  8. push 时的 `getData()` 全量 JSON 深拷贝不变（B 不改），想省要上 E 的结构共享。

### 流式输出（AI）的前置条件

**diff 的前提是 id 稳定**。若每帧重建整棵树并重新 `generateUUID()`，diff 会退化成"全删全加"。
所以要么 id 由结构路径派生（`n0-1-2`），要么增量 patch AST 而不是重建。
另外流式期间不要每 chunk 推一次 history（`patch(target, {history:false})`），否则一次生成
会留下上百个 undo 步。

### 落地顺序（每一步可独立验证）

1. `diffTree` 纯函数 + property test（随机同 id 空间的两棵树：`apply(diff(a,b), a)` 后 deepEqual b）。
2. `applyTreeOps` 接上 map，但结尾仍跑 `refresh` 交叉校验（dev only）—— 这步会暴露上面所有坑。

4. `restore()` 切到 patch，保留 `resync → refresh` 兜底；跑全量 161 + 截图测试。

### 追问：`diffRefresh` 能否"完全不干扰以前的逻辑"？→ **能，但契约要复制**

文件层面可以做到零侵入：`src/utils/treePatch.ts` + `src/plugin/diffRefresh.ts` 两个新文件，
只用现有 instance 方法（`createWrapper`/`addChildDom`/`removeNodeDom`/`shapeTpc`/`linkDiv`/
`expandNode`）。`install(plugin)`（`interact.ts:266`，实现就是 `plugin(this)`）是公开入口，
宿主自愿装；不装 = 今天行为，161 测试不受影响。

但接进 undo/redo 后有 **3 个契约必须显式复制**：

1. **`refresh` 事件 + `restoring` 标志**（本轮核对出的事实，仓库此前刚提交 `de6da95`）：
   - `interact.ts:516` 只在**传 data** 时 `bus.fire('refresh')`；`operationHistory.ts:203` 监听它，
     `handleRefresh`（:64）re-baseline `currentSnapshot`。
   - `restore` 用 `restoring = true` 包住 `mei.refresh(snapshot)`（:109-111），专为**抑制那次白克隆**
     （`getData()` 是完整 JSON 深拷贝）。
   - **基线正确性不依赖该事件** —— `restore` 自己会 `currentSnapshot = snapshot`（:131），所以
     diffRefresh 不 fire 也不会漂移。但不 fire 的代价是：① 丢掉 `refresh` 这个**公开**事件的
     宿主可见语义（pubsub.ts:89-92「A new document was installed」）；② 失去抑制机会 → 每次 undo
     多一轮全树克隆，把收益吃掉一半。→ **结论：diffRefresh 应该 fire `refresh`，并保留 `restoring` 包裹。**
2. **focus 模式**：`refresh(data)` 会 `isFocusMode = false; nodeDataBackup = nodeData`（interact.ts:514-515），
   `restore` 的 re-anchor（:105-127）建立在其上 → 第一版直接 `if (isFocusMode) return this.refresh(target)`。
3. **`arrows` / `summaries` / `meta`**：快照是全量 `MindElixirData`。**只 diff `nodeData` 会让
   "undo createArrow" 变成 no-op** → 第一版必须整体赋值 + `renderArrow()`/`renderSummary()`
   （二者是 `innerHTML=''` 全量重绘，但复杂度是 O(箭头数) 而非 O(节点数)，可接受）。
   另外 `clearSelection()`（interact.ts:500）是 refresh 的第一步，diffRefresh 不该清选区
   （保留焦点正是它的价值），但必须 sweep 掉被删节点在 `currentNodes` 里的残留 → 等于给 map 侧
   补一个 `unmountUnseen`。

核心逻辑的真实改动只有一行：`restore` 里
`mei.refresh(snapshot)` → `mei.diffRefresh?.(snapshot) ?? mei.refresh(snapshot)`（保留 restoring 包裹）。

**被否掉的"更零侵入"方案**：插件里 monkey-patch `mei.refresh`（传 data 时走增量）。代价是破坏
`refresh` 的文档语义、与 `handleRefresh` 的 `restoring` 配合变脆、debug 时看不出谁改了行为。

顺带核对：outliner 的 `bindToLiveTree`（`Outliner.ts:359-369`）用
`if (this.items?.[0] !== nodeData)` 判断，**引用不变是 no-op、换了树才 re-point**，所以
"diffRefresh 就地改而不换 `nodeData` 对象"对 outliner 无影响（它另有 `stack.subscribe` 通道）。

### 契约收敛（用户澄清：undo/redo 可以直接走 diffRefresh，**`mei.refresh` 本身一行不准动**）

| # | `refresh(data)` 的行为 | diffRefresh 必须 |
|---|---|---|
| 1 | `clearSelection()`（interact.ts:500）→ 经 viselect 的 move 回调 fire `unselectNodes`（`selection.ts:63-66`），以及 `unselectSummary`/`unselectArrow` | 镜像也清 —— 否则宿主少收事件。restore 之后本来就会重选；"保留选区"属后续**有意的行为变更**，要进 CHANGELOG |

| 3 | `bus.fire('refresh')`（:516，仅传 data 时） | 必须 fire；且保留 restore 的 `restoring` 包裹 |
| 4 | `data = JSON.parse(JSON.stringify(data))`（不污染调用方对象） | **语义不能省**，但可以只克隆"真正挂进 live tree 的部分" |

| 6 | `layout()` + `linkDiv()`（后者末尾 fire `linkDiv`） | 换 scoped linkDiv，但 `linkDiv` 事件仍要 fire 一次 |

### 最核心的一条：diff/patch 的语义是**数据顺序**，不是**渲染容器**（这轮唯一的真实返工）

第一版把 **SIDE 布局的分区做进了 `diffTree`**：按 `.lhs` / `.rhs` 各自做反向游标重排。
错在两处，而且是叠加的：

1. **纯层直接不收敛**：一个父节点的 `children` 是一个共享数组，两个容器各自有序**推不出**
   整体顺序。`[a0,b1,c0] → [c0,b1,a0]` 时按容器排能给出 `.lhs=[c,a]`，但数据落成 `[b,c,a]`，
   不等于快照。property test 直接红。
2. **DOM 层把节点搬错侧**：`move` op 的 `before` 锚点在另一个容器里，`anchorWrapper.parentElement.insertBefore()`
   就把节点插进了对面的容器（`.rhs` 空、`.lhs` 多一个）。

**修正后的分层（这才是对的）**：
- `diffTree` 只对齐**数据顺序**，完全不看 layout（`children` 数组是唯一真源）。
- `applyTreeOps` 负责映射：容器由 `node.direction` 决定（`mainContainerOf`），**槽位由数据顺序推**——
  在 `parentNode.children` 里从该节点往后找**第一个有 DOM 且同容器**的兄弟，插到它前面；
  找不到就 append（首/尾两种情况都是对的）。
- `DiffOptions.sideLayout` 因此只剩一个作用：主节点缺 `direction` 时 resync（理由见下）。

**验收方式（值得抄）**：把 DOM 层临时改回锚点定位，harness 立刻红，报出
`[m1,m2,m3] → [m2,m3,m1]` 的撤销里 `m2` 掉进 `.lhs`、`<div class="me-main rhs"></div>` 空掉。
改回即绿。**新测试必须能失败，这条做到了。**

### 其余 load-bearing 不变量（都吃过亏）

- **op 发射顺序 `insert → move → remove → update`**：insert 先行使 move 能指向新父（`insertParent` 的 redo）；
  move 先于 remove 使节点能从待删子树里被"救出来"（`insertParent` 的 undo 就是这个形状）；
  update 最后使 `expanded` 变化时结构已就位。
- **仿真层（`simChildren` / `simParent`）**：与发出的 op 同步变更，所有 index/anchor 都读它，长批次才"构造即正确"。
- **`children` **键**也要 op**：`getData()` 区分"从未有子节点"（无键）与"失去最后一个子节点"（`children: []`），
  结构 op 只能把数组缩到 `[]`，增删键必须显式 `{ type:'children', present }`。
- **`clonePatch` 不能用 `deepClone`**：后者是 JSON round trip，会丢掉 `expanded: undefined`，
  而"清空一个字段"恰恰只由那个 `undefined` 表达。
- **数据索引与 DOM 索引必须分开**：折叠隐藏的节点没有 DOM 但数据仍要改；只从 DOM 反查会静默跳过 op。
- **`mei.nodeData` 就地改，不换对象身份**：outliner 的 `bindToLiveTree` 与 focus 的 `nodeDataBackup` 都靠引用。

### resync（降级）规则的两次收紧

- **只在主节点上**：`direction` 变 = resync，仅当该节点在任一树里是**根的直接子节点**。
  深层节点的 `direction` 对渲染完全惰性，当作普通 `update` 处理。
  **理由是一条实测出来的库行为**：`objectManipulation.moveNodeObj` 会把目标的 `direction`
  复制给**任何被移进主节点的节点**（`nodeManipulation.ts:38` 那个分支对 `type:'in'` 也生效），
  于是"拖一个叶子进主节点"之后它的 `direction` 就变了。若按"任何 direction 变化都 resync"处理，
  **每一次普通拖拽的撤销都会退化成全量重建**——正好把这次工作的收益全吃掉。parity harness 抓到的。
- **主节点缺 side 也 resync**：`layout()` 渲染时会**写回**缺失的 `direction`（`layout.ts:26-40` 按左右计数交替分配），
  这是对调用方数据的写入，本地 op 复现不了 → 打了 `sideLayout` 就 resync。

### 顺手核对出的两个库内既有问题（**未改**，属越界）

1. **`setNodeTopic` 不 fire `operation`**（`nodeOperation.ts:339`），只改 topic + `linkDiv()`。
   后果：这次编辑不进历史栈，而且**下一次操作的快照早于它** → 撤销下一个操作会连带把它回滚掉。
   库自己的 outliner 早就绕开了（`Outliner.ts:475` 注释："reshapeNode (not setNodeTopic) — it fires the tracked 'reshapeNode'"），
   但它仍在 `index.ts:236` 作为公开 API 声明着。harness 里保留了一条这个路径（标注为 untracked），
   用来压 diff"要能还原历史栈外的改动"。
2. **`moveNodeObj` 给深层节点写 `direction`**（同上）：渲染惰性、但会出现在 `getData()` 里。
   diff 现在按普通字段 update 处理，不因此重建。

## 订正：`expandNode` 那条"有意新增"是错的，已删掉（本轮实测）

**初稿错在哪**：设计阶段断定"增量路径必须显式 `bus.fire('expandNode')`，因为 outliner 靠这个事件同步折叠"，
于是代码里加了这一行，并在 harness 里把该事件放宽成 `fast >= slow` 来自圆其说。

**实测推翻**：

1. 把那行注释掉 → `tests/outliner.spec.ts` **7/7 全绿**（含 `Map collapse is undoable and the outline follows`）。
   读码确认原因：`Outliner.ts:151` `this.stack.subscribe(this.requestSync)`，注释写着
   "map operations, undo, redo and clear **all land here**"；`Outliner.ts:160` 的 `expandNode`
   监听器注释写着它是给 **SILENT** expand 用的（静默展开不产生自己的历史条目）。
   → **undo/redo 走历史栈通道，根本不经过 expandNode。**
2. 再查"多发这个事件会不会让 outliner 多渲染一次"（那才是 add 这行的代价）：
   给 `probe-sync-counts.mjs` 补了场景 6b「折叠的 undo/redo」，
   **带这行 22/22，删掉这行也 22/22** —— `scheduleSync` 的微任务请求被 `requestSync` 的同 tick 渲染吸收掉了。
   → 这行对**仓内所有消费者都是惰性的**。

**结论与动作**：
- 删掉 `mei.bus.fire('expandNode', node)`，并留注释写明"为什么这里故意不 fire"（防止后人"好心"加回来）。
- harness **恢复严格比较**：现在每个总线事件（含 `expandNode`）都逐条相等，23/23 通过。
  等于把一个"放宽的断言"换成了一个"真断言"。
- CHANGELOG 的 Behavior Changes 里那条"撤销折叠会 fire `expandNode`"**整条删除**（不再有该行为）。

**方法教训（比这个 bug 本身值钱）**：
**放宽一个断言，必须是"实测出来的机制"在支撑，不能是"听起来合理的故事"在支撑。**
这行的依据从头到尾只是一句叙述；`fast >= slow` 在 slow 恒为 0 时更是恒真 ——
**一个恒真的断言不是弱断言，是假断言**。给任何"有意差异"写断言前，先找出它的消费者并实测一次。
同类陷阱：`Outliner.ts` 的注释/`probe-*` 脚本里的既有结论是**可以引用但必须复核**的二次信息源。

### 探针挖出的额外一条：`onChange` 漏掉「大纲内改文字」

`OutlinerOptions.onChange` 的注释写的是 "after every change that reached the outline"，实测**不成立**。
边界（探针 17/17）：

| 变更 | 进 map + journal | 触发 onChange |
| --- | --- | --- |
| 大纲里的结构手势（加/缩进/移动/删除/折叠） | ✔ | ✔ |
| undo / redo | ✔ | ✔ |
| map 侧改动（含程序化 `reshapeNode`） | ✔ | ✔ |
| **在大纲里改某行文字** | ✔（journal 里是一条 `reshapeNode`，`Ctrl+Z` 能回滚） | **✘** |

原因：文字编辑在 blur 时经 `setNodeTopicBound` 提交，而它把 `reshapeNode` 包在 `suppressSync = true`
里（避免整树重渲染吞掉导致 blur 的那次点击），`emitChange()` 又只挂在渲染路径上 → 通知丢失。
需要完整信号就用 `mei.historyStack.subscribe(() => save(outline.getData()))`。
**已写进 skill §5 的表格 + 记为已知缺口；源码注释我故意没改** —— 这更像是"行为与注释不一致"，
改行为还是改注释该由作者定，已在回复里提出来。
