## Outliner 折叠按钮 hover 无手型光标（修复）

**报告**：outliner 的折叠 chevron 悬停时没有可点击 cursor。

**定位**：`src/outliner/outliner.css`。`.outline-item-menu-btn` 在自己的规则里声明了
`cursor: pointer`，`.outline-item-collapse-btn` 没有 → computed 值 `auto`。

根因与 09-14 那次「按钮渲染成带边框灰方块」是同一个：react-outliner 依赖 Tailwind
preflight 提供按钮的基底样式，包括 `button` 的可点击光标。mind-elixir 不带 preflight，
117-134 行那个 reset 块中和了 UA 的 border/padding/appearance/background，但没人恢复
cursor。所以 `…` 看起来可点、chevron 看起来不可点，是同一个缺口的两半。

**改动**：
- `.outline-item-collapse-btn` 基础规则加 `cursor: pointer`（挨着 `pointer-events`）。
  默认态 `pointer-events: none` 时它不参与命中，等于惰性；expanded/collapsed 打开事件后
  继承生效 —— 这正是需要的两个状态。
- 扩展 reset 块上方的注释，说明 cursor 同属那个 preflight 缺口。
- 回归测试 `tests/outliner.spec.ts:277` 《The collapse chevron shows a clickable cursor》：
  断言 `data-state='expanded'` + computed `cursor: pointer`，再 hover 行、把鼠标移到
  chevron 几何中心，用 `document.elementFromPoint` 读**指针底下那个元素**的 cursor（用户
  真正看到的光标属于命中元素，不属于按钮本身），最后断言邻座 `…` 也是 pointer —— 那条
  存在的 contrast 正是这次缺失的。
- CHANGELOG `## Unreleased` → Bug Fixes 加一条。

**负面控制**：把 `cursor: pointer` 改成 `auto`，该测试如期失败（`Expected: "pointer"`,
`Received: "auto"`），恢复后通过。

**绿色检查**：playwright 188 passed（原 187 + 新增 1，17.1 s）、`tsc --noEmit -p
tsconfig.json` 0、`tsc -p tsconfig.type-test.json` 0、`pnpm build` 0。`dist/Outliner.css`
与 `dist/MindElixir.css` 都含 `outline-item-collapse-btn{…;cursor:pointer;…}`。

**顺带确认不是 bug 的一点**：btn-group `opacity: 0` 时按钮仍 `pointer-events: auto`，
理论上会拦截点击，但按钮在 wrapper 子树内，指针进入即让 wrapper `:hover` 成立 → 组立即
变 opacity 1，所以不存在「点到不可见按钮」。不必改。

## 折叠行的 `…` 菜单不再常显（修复）

**报告**（截图）：被折叠的行旁边挂着一个灰色的 `…`，只有 chevron 是蓝的。

**定位**：`src/outliner/outliner.css` 那条 reveal 规则的第 4 个分支
`.outline-item-btn-group:has([data-state='collapsed'])`。它的本意是「折叠行必须常显 chevron
（否则看不出下面藏着东西）」，但它作用于整个按钮组，`…` 被一起拉亮；而 `…` 的表面色只在
`:hover` / `:focus-within` 时画，所以静止态下就剩一个没有底色、也没有 hover 的裸字形。
截图里 `…` 没底色 → 那一行既没 hover 也没 focus，纯靠折叠分支亮着。

**改动**：只让 chevron 回答折叠状态，`…` 保留和其他行一样的三条信号。加一条把 `…` 单独
调暗的规则（不动组的 opacity，所以 chevron 不会位移）：

```
.outline-item-wrapper:not(:hover):not(:focus-within):not(.menu-open)
  .outline-item-btn-group:has([data-state='collapsed'])
  .outline-item-menu-wrapper { opacity: 0; }
```

挂在「行的状态」上而不是和组规则比特异性，是有意的：指针进入那个字形所在的格子本身就会让
`wrapper:hover` 成立，所以不存在「看不见但可点」。`.outline-item-menu-wrapper` 顺带补了
`transition: opacity 0.2s`，跟组的淡入同步（否则 `…` 会是硬闪）。`menu-open` 仍然保留：
折叠行上开着菜单时不能被调暗（例如菜单开着时从别处把该节点折起来）。

**回归测试** `tests/outliner.spec.ts`《A folded row keeps its chevron and drops the `…`
while at rest》：折叠从 **map** 侧发起（点 chevron 会把 focus 留在按钮上，`:focus-within`
会让 `…` 亮着，不是要复现的状态），再 `page.mouse.move(0,0)` 把指针挪开，断言
（a）chevron `data-state=collapsed` 且底色非 transparent（折叠分支的正面控制：不能被误删），
（b）组 `opacity: 1`，（c）`…` wrapper `opacity: 0`，最后 hover 行断言 `…` 回到 1。

**负面控制**：把新规则的 `opacity: 0` 换成 `1`，该测试如期失败；恢复后通过。

**绿色检查**：playwright 189 passed（188 + 新增 1，16.3 s）、`tsc --noEmit -p tsconfig.json` 0、
`tsc -p tsconfig.type-test.json` 0、`pnpm build` 0。`dist/Outliner.css` 与 `dist/MindElixir.css`

## 「行控件该不该改用 JS 控制」——实测：不会更快（探针 v2）

**起因**：用户问「CSS 写得这么复杂，用 JS 控制是不是性能更好」。

**做法**：`/tmp/probe-row-controls.mjs`（已存入
`~/.workbuddy/skills/mind-elixir-perf-probe/scripts/probe-css-vs-js-control.mjs`），
1365 行 / 21848 DOM 元素，`/test.html` 起真实例，CDP `Performance.getMetrics` 拆
RecalcStyleDuration / LayoutDuration / ScriptDuration / TaskDuration，另加 Node 侧墙钟。
变体：shipped / 去掉新规则 / perChild（无 `:has()`）/ JS 控制 / floor（完全不高亮），
**同一份文档内用 CSSOM deleteRule+insertRule 来回切规则**，预热两轮，末尾复测 shipped 做漂移对照。

**结果**（hover 变更单次；两次 shipped 的差即噪声 ±0.05 ms recalc / ±0.6 ms task）：

| 变体 | render | recalc | task | script | 单次折叠 recalc |
| --- | --- | --- | --- | --- | --- |
| shipped | 0.265 | 0.20~0.25 | 4.0~4.6 | 0.5 | 0.020 |
| noNewRule | 0.295 | 0.21 | 3.7 | 0.5 | 0.018 |
| perChild | 0.28~0.36 | 0.20 | 4.5 | 0.45 | 0.011 |
| js | 0.275 | 0.21 | 4.5 | **4.1** | 0.013 |
| floor | 0.265 | 0.18 | 4.6 | 0.4 | 0.009 |

- reveal 类选择器**不计成本**：floor（完全不高亮）也没比 shipped 快出噪声；`render()`、
  折叠路径（几十 µs）都不受影响。hover 的 recalc 由别的规则与该行自身重算主导。
- **JS 更贵**：inline style 一样触发失效重算，还多出事件派发 + 回调（script 4.1 vs 0.5 ms/次）。
  没有任何指标显示 JS 更快。
- 真正反对 JS 的理由是**谁持有状态**：CSS 的状态就是浏览器的 `:hover`/`:focus-within`；
  JS 要自己重建状态机，而行元素是按 key 复用的 → 移动/缩进/重渲染后 inline 样式得重新推导。
- **perChild 是"更简单"的正解而不是"更快"的正解**：把组级 opacity + `:has()` 换成每个子元素
  自己的 opacity，删掉 `:has()` 和那条 `:not()` 链，删的是机制而不是行为
  （行为矩阵只差「组自身 opacity」这一项，属于机制差异）。换它的理由是**可读性**。
  真换的话 `tests/outliner.spec.ts` 里两条断言组 opacity 的用例要改成断言子元素的有效可见性。

**探针踩的坑（都写进 skill 了）**：① 每个变体重载页面 → 方差吃掉 0.05 ms 级差异（v1 因此得出
"perChild 快 25%" 的假结论）；② `resetRules` 不先把上一张还原表的规则收回来，就会在「本轮没删规则」
的变体里把规则彻底弄丢（症状：对照变体自己和自己不一致）；③ 比耗时前必须先用
「状态 × 属性」矩阵证明行为等价（读**有效可见性** = 自身 × 祖先 opacity，CSS 版本常靠父级隐藏）；
④ JS 变体要写成 JS 能写的最省版本（`matches(':hover, :focus-within, .menu-open')` 交回引擎）
才算公平——v1 的 JS 变体漏了「指针移开后 focus 仍要保持」和「hover 折叠行该露出 `…`」，
拿功能更少的实现比耗时会得出 JS 更快的假结论。
另修正 skill 一条笔记：`ScriptDuration` 并非恒为 0 —— 真实输入事件触发的脚本会计入
（CDP `mouse.move` → `mouseover` 监听器），但和 `TaskDuration` 仍对不上，只能当方向性指标。

## 行控件 reveal 机制改写（可读性）：组级 opacity + `:has()` + `:not()` 链 → 行级自定义属性

**起因**：用户「你能提高现在 css 的可读性吗？」（上一轮我说过 per-child 是更干净的正解）。

**改法**（`src/outliner/outliner.css`）：旧的机制要三处配合——组 `.outline-item-btn-group{opacity:0}`、
reveal 规则带第 4 条 `:has([data-state='collapsed'])` 臂、再加一条
`:not(:hover):not(:focus-within):not(.menu-open) ... :has(...) .outline-item-menu-wrapper{opacity:0}`
去把 `…` 从折叠臂里挑出来。现在：

```css
.outline-item-wrapper { --row-control-opacity: 0; }
.outline-item-wrapper:hover, :focus-within, .menu-open { --row-control-opacity: 1; }
.outline-item-collapse-btn, .outline-item-menu-wrapper { opacity: var(--row-control-opacity); }  /* 跟随行状态 */
.outline-item-collapse-btn[data-state='collapsed'] { opacity: 1; ... }                            /* 显式例外 */
```

- 信号只写一次；`…` 不必再被"挑出来"，它本来就不在那条例外里。`:has()` 和 `:not()` 链全消失
  （`outliner.css` 里已无 `:has()`；组只剩几何）。状态规则从 4 处散落收拢成一个
  「═══ Row controls: state ═══」区块，几何（组 / menu-wrapper / menu-btn）在它前面。
- 顺手删掉 `.outline-item-collapse-btn:hover{background-color:…}`：指针压在字形上时
  `wrapper:hover` 必然成立，那条完全冗余。
- **负面控制暴露的洞察**：`[data-state='collapsed']` 里的 `opacity: 1` 一开始是冗余的
  （消费规则只选 `[data-state='expanded']`，折叠态本就不在里面）→ 删掉它测试照样绿。
  于是把消费规则收成 `.outline-item-collapse-btn`（不带属性选择器），让那条 `opacity: 1`
  **变成承重的显式例外**，负面控制这才失败。**一条改不动任何测试的声明，要么删掉要么让它承重。**
- 自定义属性能带动 `opacity` 过渡：`transition` 挂在元素自己的基础规则上（不是挂在
  `[data-state='expanded']` 那条），否则折叠时 state 一换、`transition` 一起失效 → 瞬变。
  实测两个引擎都是 0.07→1.00 的 200 ms 淡入。

**验收**：`probe-row-control-parity.mjs`（已存 `mind-elixir-parity-harness/scripts/`）——
chromium + webkit，9 个状态（rest / hover-topic / focus-no-hover / hover-chevron /
hover-menu-spot-on-collapsed / menu-open-forced / collapsed-rest / collapsed-hover / re-expanded）
× 87~88 行，「有效可见性 / 背景色 / cursor / 几何」逐字段全等；789 个样本的原始 `opacity`
不同（机制差异，报告但不判等）。测试侧：3 处断言从读组 `opacity` 改成
`expectVisibleOpacity`（祖先链乘积 + `expect.poll`）；两条负面控制（删信号规则 / 删折叠例外）
都如期失败。全绿：**189 passed** + 两个 tsc 0 + build 0；`dist/Outliner.css`、`dist/MindElixir.css`
都有 `--row-control-opacity`、都没有旧 `:has`/`:not` 链，`dist/Outliner.js` 仍不含 map 代码。

**自己踩的两个坑（都写进 parity harness 技能了）**：① 探针第一版崩在中途且没有 `finally`，
把工作树留在了旧 CSS 上，于是第二版「新版」读到的其实是旧内容 → 自己和自己比，报
"逐字节相同"。② 负面控制那轮跑完，探针把**故意做坏的**变体写回了工作树（`finally` 恢复的是
"传入的新版"而不是"开工前那一份"），接下来两次测试失败（点 `…` 超时、hover 不亮）全是自己的
作案现场。修法：开工前存 `ORIGINAL`、`finally` 写回它、跑前断言"工作树 == 新版"、跑完断言
"工作树 == ORIGINAL"；再加一条**变体见证**（读只存在于新版的 `--row-control-opacity`，
旧版必须每个状态都读不到）。

## 历史回退不重绘（reshapeArrow / 箭头·摘要整层）

**症状（用户报）**：`reshapeArrow` 回退「没有反应」。探针确认：拖动控制点（或直接调 API）后
Ctrl+Z，`getData().arrows[0].delta1` 已经回退，但 `<g data-linkid>` 的 path `d` 一动不动。

**根因**：`diffRefresh` 把 `this.arrows` / `this.summaries` 整个替换掉，而重绘的触发条件是
`applyTreeOps` 末尾的 `if (ops.length) mei.linkDiv()`。箭头/摘要在 `nodeData` **之外**，
`diffTree` 看不见 —— 「只改链接层」的操作 diff 出来是**空 op 列表**，于是数组换了、画面没重画。
`linkDiv` 正是 `renderArrow()` / `renderSummary()` / 清空 `labelContainer` 的唯一入口；同一条路上
`refresh()` 永远重画，所以旧路径是对的、被 diffRefresh 快路径漏掉了。

**修复（两处）**：
1. `diffRefresh`：替换前用 `sameValue` 比较 arrows / summaries，变了才替换并置 `linksChanged`，
   再传给新参数 `applyTreeOps(mei, ops, redraw)` → `if (ops.length || redraw) mei.linkDiv()`。
   内容相同时**不替换**，DOM 里 `<g>.arrowObj` 就不会指向数组外的孤儿对象（否则拖控制点会写到
   孤儿上，操作记录成"没变化"）。`sameValue` 由 treePatch 导出（该模块不在公开导出面）。
2. `operationHistory.restore`：`document.querySelector('#a-…' / '#s-…')` →
   `mei.nodes.querySelector`（**第二个独立缺陷**）。多实例同页时 id 全局查询会选到另一个 map 的
   箭头，`slow.selectArrow(fastGroup)` 把高亮画到别人身上。parity harness 一加箭头操作就暴露了。

**回归测试**：`tests/diff-refresh.spec.ts` 的 operations 追加 `reshapeArrow`（控制点 / 标签+样式）、
`createSummaryFrom`、`removeSummary`。负面控制（`git stash push` 只回退 diffRefresh + treePatch）
该 spec 立刻变红：`linkDiv fired 0x vs 1x` + arrows / summaries / labels 快照不符；恢复后 3 passed。

**harness 侧的两处归一化（测试事实，不是库行为）**：
- `.linkcontroller` + `P2/P3`：选中箭头时 `showLinkController` 把它们 append 进 `.me-nodes`，
  而 `layout()` 重建 `.me-nodes` 会把它们挤掉 → 两条路径挂载位置不同。都 `display:none`、也不从
